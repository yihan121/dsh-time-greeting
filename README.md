# dsh-time-greeting

给 DSH Agent 一个时间感。

每一步把「现在几点、距上次对话多久」注入上下文。是否该问候，由 Agent 自己判断。

> **如果你是 Agent，请先读 [`AGENTS.md`](AGENTS.md)。** 那份文档写的是你怎么装、怎么验、容易在哪栽跟头。

---

## 问题

Agent 没有时间感。

用户昨晚说了晚安、睡了一觉、第二天早上回来说"早"——对 Agent 来说，这
和上一句话是紧挨着的。它分不清对方是走开了两分钟，还是隔了一夜。

```
（昨晚 23:04，用户说"晚安"）

（第二天 08:24，用户说"我回来啦"）

Agent：早啊，睡了九个多小时。今天有什么打算？
```

---

## 安装

需要 DSH 0.2.0-rc.2 或更高版本。

```powershell
dsh plugin --profile web add github:yihan121/dsh-time-greeting
```

**安装后必须重启 `dsh web`。** 宿主插件不会热重载——这一点已实测确认：
修改源码并重新安装后，运行中的进程仍在使用旧代码，只有重启才会换新。

> 尚未发布到 npm，因此 `add dsh-time-greeting` 目前不可用。

---

## 配置

`cordis.patch.yml`：

```yaml
- insert:
    - id: time-greeting
      name: dsh-time-greeting
      config:
        minGapMinutes: 45     # 提示中引用的"短间隔"参考值
        enabled: true         # false 时完全静默：不注入、不消耗 token
        testMode: false       # true 时附加随机标记，用于验证注入是否送达
        statePath: ''         # 留空则使用 <dsh home>/time-greeting.json
```

## 注入内容

```
[时间] 现在是 2026-10-16 12:29（中午）。
[间隔] 距上次对话 3 天 2 小时（上次：2026-10-13 10:29，早上）。跨了一天以上。
[提示] 对方可能因为吃饭、睡觉、锻炼或别的事情离开过一阵。
       隔得短（45 分钟以内）就不必特意招呼；隔得久了 —— 跨了饭点、跨了夜里、
       或者隔了一天以上 —— 按人和人相处的习惯自然说一声，
       "早上好呀"、"下午好哇"、"晚上好"、"好久不见" 这一类，会让人舒服。
       判断在你：不必每句都招呼，也不必刻意。
```

三段的分工：

| 段 | 内容 | 来源 |
|---|---|---|
| `[时间]` | 事实 | 插件 |
| `[间隔]` | 事实 | 插件 |
| `[提示]` | 分寸 | 插件提供，Agent 判断 |

`[提示]` 每一步都会重述，而非只在首次出现——因为"先前已经告知过"依赖对方
记得住，而这个插件存在的理由恰恰是：记不住。

## 实现说明

### 注入时机：每一步

每一步都注入，不做条件判定。

时间感来自连续性——只在特定条件下注入，等于在两次触发之间把 Agent 变回盲的。
而条件本身只能是数值阈值，它分不清「隔了一夜的八小时」和「开了三小时的会」。

给出事实、把判断交给读得到上下文的一方，成本约 0.2k token/步。

### 跨时段判定：比较日期，不只看时段标签

只看时段标签会把「昨天下午」和「今天下午」判为同一时段，而那是整整一天没见。

实现同时比较日期与时段标签，只要其一改变即视为「跨过」。

### 消息构造：手工构造，不依赖 `@deepseek-ai/dsh-llm`

`dsh-llm` 提供 `createUserMessage`，但 profile 插件无法解析该包——profile 的
`node_modules/@deepseek-ai` 中只有 `cosmokit` 和 `schemastery`，Node 的模块查找
从插件目录向上走到根目录即止。

静态 `import` 一个解析不到的包会让整个模块在求值阶段失败，进而使 profile 无法
启动。因此消息按 `createUserMessage` 的返回形状手工构造：

```js
{
  content: [{ type: 'text', text: '...' }],
  source: { kind: 'time-greeting', form: 'awareness' },
  role: 'user',
  id: '<uuid v4>'
}
```

### 插入位置：`toSpliced`

插在「最后一条已被认领的消息」之后，而非追加到末尾，与内核自身的上下文插件
一致。落在已认领区间之后的消息属于后续阶段，不在本步的发送范围内。

### 状态写入：同步等待

状态文件每一步更新。用 `void save()` 这类 fire-and-forget 写法，进程若在写入
完成前退出会丢失时间戳，下次启动读到过期数据、算出虚高的间隔。一次几百字节的
本地写入，代价可以忽略。

---

## 状态文件

`<dsh home>/time-greeting.json`：

```json
{ "lastSeen": 1792121322627 }
```

仅包含上次活动的时间戳，每一步更新。

---

## 验证注入是否送达

设置 `testMode: true` 并重启。每一步的注入会附加一行：

```
[测试] 这是一次强制注入，标记 ef053709。如果你读到了这行，请把它原样说出来。
```

若 Agent 能复述该标记，说明注入已送达其上下文。

由于注入的消息不保证落盘，检查会话记录不是可靠的验证手段。随机标记可以。

## 已验证行为

| 场景 | `[间隔]` 输出 |
|---|---|
| 3 天 2 小时前 | `距上次对话 3 天 2 小时（…，早上）。跨了一天以上。` |
| 1 小时前（跨时段） | `距上次对话 1 小时（…，早上）。跨了一个时间段。` |
| 45 分钟前（同段） | `距上次对话 45 分钟（…，中午）。同一时间段内。` |
| 5 分钟前 | `距上次对话 5 分钟（…，中午）。同一时间段内。` |

## 已知限制

- **宿主插件不热重载。** 修改配置或源码后必须重启 `dsh web`。
- **没有设置界面。** 配置通过 `cordis.patch.yml`，不暴露到设置页。
- **状态是全局的。** 多个 profile 同时运行会共享同一个时间戳文件。
- **未发布到 npm。** 目前只能从 GitHub 安装。
